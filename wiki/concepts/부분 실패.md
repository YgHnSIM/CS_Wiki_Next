## 개요

[[부분 실패]]는 분산 시스템에서 전체 시스템이 한꺼번에 정상 또는 고장 상태가 되지 않는 조건을 말한다. 어떤 서버는 요청을 처리하고 다른 복제본은 지연되거나 접근할 수 없으며 네트워크 경로는 한 방향으로만 손실되고 호출자는 시간 초과만 관찰할 수 있다. 이때 한 곳에서 본 실패 신호를 전체 작업의 실패·성공·상태 손실과 동일시할 수 없다.

[[Time, Clocks, and the Ordering of Events in a Distributed System]]이 보여 주듯 분산 사건에는 자연스러운 하나의 전역 관찰 순서가 없다. [[Implementing Remote Procedure Calls]]의 RPC는 응답을 받지 못한 호출자가 서버 미수신·처리 중 실패·처리 후 응답 유실을 즉시 구분할 수 없음을 구현 문제로 드러낸다. [[The Google File System]]과 [[Dynamo - Amazon's Highly Available Key-value Store]]는 구성 요소 실패를 예외가 아니라 정상 운영 조건으로 두는 저장 시스템 사례다.

## 관찰과 실제 상태의 차이

| 관찰한 현상 | 가능한 실제 상태 | 설계에 남는 질문 |
|---|---|---|
| 클라이언트 시간 초과 | 요청 미도착, 서버 처리 중단, 처리 완료 뒤 응답 유실 | 재시도하면 중복 부작용이 생기는가 |
| 한 복제본의 읽기 실패 | 다른 복제본은 최신·오래된 값·충돌 버전을 가질 수 있음 | 어떤 읽기를 성공으로 볼 것인가 |
| 일부 노드와 통신 단절 | 노드 고장, 경로 분할, 긴 지연, 부하 포화 | 대기·거부·우회·복구 중 무엇을 할 것인가 |
| 복제 지연 또는 충돌 | 같은 키의 여러 버전이 살아 있을 수 있음 | 병합 책임과 사용자 노출 규칙은 무엇인가 |
| 복구 후 재접속 | 이전 요청의 결과가 뒤늦게 나타날 수 있음 | 요청 식별자·멱등성·보상 처리는 어떻게 정하는가 |

이 표는 특정 관찰에서 모든 가능성을 추론할 수 있다는 뜻이 아니라 관찰만으로 구분할 수 없는 상태가 남는다는 뜻이다. 설계는 그 불확실성을 없앤다고 주장하기보다 어떤 조건에서 재시도·중복 제거·충돌 병합·사용자 확인으로 다룰지 계약해야 한다.

## 실패 모형과 서비스 결과

부분 실패는 하나의 장애 모형 이름이 아니라, 실패 관찰과 전체 상태가 분리되는 운영 조건이다. 정지 장애, 네트워크 분할, 메시지 유실·중복, 느린 노드, 저장 복제 지연은 서로 다른 대응을 요구한다. [[복제 로그와 합의]]의 crash fault 가정이나 [[CAP 정리]]의 분할 모형은 그중 일부를 형식화하지만, 사용자에게 보이는 오류·기한·복구는 별도 서비스 계약이다.

따라서 “고장을 견딘다”는 주장은 다음을 함께 밝혀야 한다. 어느 구성 요소와 경로가 실패할 수 있는지, 요청을 언제 성공·실패·미확정으로 응답하는지, 중복·오래된 읽기·충돌을 누구에게 드러내는지, 그리고 어떤 검증 뒤 안전한 상태로 되돌아오는지다.
