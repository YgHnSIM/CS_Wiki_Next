## 개요

[[재현 가능한 빌드]]는 특정 소스 코드, 빌드 환경, 빌드 지침에서 지정한 산출물을 다시 만들었을 때 bit-by-bit 동일한 결과를 얻는 성질이다. 핵심은 “한 번 성공한 빌드가 다시 실행된다”가 아니라, 독립된 사람이 빌드 경계를 이해하고 산출물의 동일성을 검증할 수 있다는 점이다.

여기서 빌드 환경은 컴파일러와 링커만이 아니다. 실제 결과에 영향을 주는 의존성 버전, 빌드 플래그, 환경 변수, locale, 경로, 파일 순서, timestamp와 같은 요소가 포함될 수 있다. 반대로 모든 호스트 차이를 제거해야 한다고 미리 가정하지 않고, 어떤 요소를 환경의 일부로 고정할지 먼저 선언해야 한다.

## 계약의 구성

| 계약 항목 | 고정하거나 기록할 것 | 실패 예 |
|---|---|---|
| 소스 | 버전 관리 revision 또는 소스 archive | 같은 태그가 다른 내용으로 이동함 |
| 지침 | 명령, 빌드 규칙, 설정, toolchain 선택 | 로컬 플래그나 숨은 설정이 결과에 개입함 |
| 환경 | 컴파일러·링커·의존성 버전, 필요한 환경 변수 | 서로 다른 toolchain이 코드 생성 결과를 바꿈 |
| 변동 입력 | timestamp, locale, timezone, 경로, 파일 순서, 난수, 네트워크 | 현재 시각이나 directory listing 순서가 산출물에 들어감 |
| 지정 산출물 | 실행 파일·패키지·filesystem image 등 비교 대상 | 로그와 주 산출물을 같은 기준으로 비교함 |
| 검증 | cryptographic hash 또는 byte 비교와 재빌드 절차 | “빌드가 끝났다”만으로 동일성을 주장함 |

[[SOURCE_DATE_EPOCH Specification]]은 timestamp를 현재 시각 대신 명시적 입력으로 바꾸는 좁은 표준 사례다. [[Bazel BUILD Files and Hermeticity]]는 알려진 입력과 제한된 I/O로 해석 경계를 줄이는 구현 사례다. 이 사례들이 모든 도구의 자동 재현성을 보장하는 것은 아니며, 실제 산출물 비교가 마지막 판정 단계다.

## 구별해야 할 개념

- deterministic build는 같은 조건에서 같은 결과를 만들도록 실행을 안정화하는 성질을 가리킬 수 있다. reproducible build는 그 조건과 지정 산출물을 외부 재빌더가 이해하고 bit-by-bit 비교할 수 있는 계약까지 포함한다.
- provenance는 산출물이 어디서·언제·어떻게 만들어졌는지 설명하는 attestation이다. [[SLSA Build Provenance Specification]]은 재빌드를 돕는 정보를 정의하지만, provenance만으로 산출물 동일성이 판정되지는 않는다.
- 서명과 checksum은 산출물의 출처 또는 전송 중 무결성을 확인하는 수단이다. 그것만으로 소스에서 산출물까지의 재현 가능한 경로가 성립하지는 않는다.
