## 개요

[[분산 파일 시스템]]은 파일 이름, 디렉터리, 읽기·쓰기 같은 파일 인터페이스를 유지하면서 실제 데이터와 메타데이터를 여러 컴퓨터에 나누어 관리하는 저장 시스템이다. 사용자는 파일을 하나의 논리적 객체처럼 다루지만 시스템 내부에서는 이름공간, 청크나 블록의 위치, 복제본, 캐시, 쓰기 순서, 장애 감지와 복구가 서로 다른 서버·경로에 걸쳐 작동한다.

[[The Google File System]]은 이 개념을 대규모 데이터 집약 작업의 조건에서 구체화한 사례다. GFS는 파일을 청크로 나누고 마스터가 메타데이터를 관리하며 청크 서버가 복제된 데이터를 보관한다. 클라이언트는 메타데이터를 얻은 뒤 데이터 서버와 직접 통신한다. 이 구조는 파일 인터페이스를 제공하면서도 데이터 경로·복제·장애 처리를 작업 부하에 맞게 분리한다.

## 파일 API와 저장 계약

| 층 | 주요 책임 | 파일 호출만으로 알 수 없는 것 |
|---|---|---|
| 이름공간·메타데이터 | 파일 이름, 청크 대응, 위치·임대 정보 | 현재 메타데이터 경로의 가용성과 갱신 시점 |
| 데이터 경로 | 청크·블록 읽기와 쓰기 | 어떤 복제본·네트워크 경로를 거쳤는지 |
| 복제·복구 | 사본 배치, 장애 감지, 재복제 | 모든 사본의 즉시 동일성이나 복구 완료 시점 |
| 쓰기 의미 | 순서화, 추가, 중복·충돌 처리 | 요청이 한 번만 반영됐는지와 응용 작업의 완료 여부 |
| 종단 검증 | 파일 무결성, 작업 결과, 재처리 판단 | 하위 저장 계층의 완료 신호가 응용 결과를 증명하는지 |

따라서 분산 파일 시스템의 “쓰기 성공”은 시스템마다 다른 범위의 약속이다. 클라이언트가 데이터를 전송한 것, 한 서버가 수신한 것, 선택한 복제 규칙을 만족한 것, 모든 읽기에서 곧바로 같은 결과가 보이는 것, 응용 작업이 유효하게 완료된 것은 서로 다를 수 있다.

## 작업 부하가 만드는 설계

분산 파일 시스템은 로컬 디스크를 멀리 옮긴 것이 아니다. 큰 파일의 순차 읽기, 동시 추가, 대규모 배치 작업, 작은 임의 읽기, 낮은 지연의 대화형 서비스는 서로 다른 청크 크기·복제·메타데이터·일관성 선택을 요구한다. GFS가 대용량 데이터셋과 구성 요소 고장을 전제로 인터페이스와 구현을 조정한 이유가 여기에 있다.

성능을 비교할 때도 파일 전송률 하나만으로 충분하지 않다. 파일 크기·접근 패턴·복제 수준·캐시 상태·장애 주입·읽기 일관성·쓰기 성공 조건을 함께 고정해야 한다. 그래야 높은 총 처리량이 긴 복구 시간, 약한 쓰기 의미, 특정 작업 부하에만 맞는 설계를 숨기지 않는다.
