## 개요

[[하드웨어 실행 모델]]은 컴퓨터가 명령어를 가져와 해석하고 상태를 갱신하는 물리적 동작 구조를 가리킨다. 폰 노이만 저장 프로그램 방식 이후의 컴퓨터는 회로 배선을 매번 재구성하던 방식에서 벗어나, **연산(ALU)·저장(RAM)·제어**(PC)의 세 축을 물리적으로 분리하고 단일한 메모리 주소 체계와 시스템 버스 위에서 실행을 직조하는 방식을 표준으로 삼는다.

## 실행을 움직이는 세 축

하드웨어 실행 모델을 움직이는 핵심 축은 둘(연산과 저장)이 아니라 셋이다.

| 축 | 하드웨어 담당 | 역할 | 직조에서의 비유 | 실행 모델에서의 위상 |
|---|---|---|---|---|
| **연산** | ALU + 범용 레지스터 (`RAX`, `RBX` 등) | 값을 변경한다 | **씨실** (변화의 실체) | 계산의 주체 (ALU는 레지스터만 직접 계산) |
| **저장** | RAM + 시스템 버스 | 칸을 기억한다 | **날실** (상태의 바탕) | 데이터의 거처 (바이트 주소 사물함) |
| **제어** | **프로그램 카운터 (PC / RIP)** | 다음 실행할 명령을 선택한다 | **바늘 / 북** (흐름의 지휘) | Fetch의 출발점 (제어 흐름의 지휘) |

이 직조 비유는 1843년 [[에이다 러브레이스]]가 [[해석 기관]]을 해설하며 "자카드 직조기가 꽃과 잎을 짜듯, 해석 기관은 대수적 패턴을 짠다"고 갈파했던 컴퓨터 역사의 근원적 통찰에 닿아 있다. 프로그래밍은 제어라는 바늘이 날실(저장)과 씨실(연산) 사이를 오가며 실행의 직물을 짜는 과정이다.

여기서 ALU는 RAM에 저장된 메모리 셀을 직접 계산하지 못한다. RAM의 데이터는 반드시 `LOAD` 명령을 통해 CPU 내부 레지스터로 복사된 후에야 ALU에 의해 연산되며, 연산 결과는 `STORE` 명령을 통해 다시 RAM으로 복귀한다.

## Fetch–Decode–Execute와 버스 분업

명령어가 메모리에 적재되고 CPU가 이를 실행하는 과정은 3단계 사이클로 회전한다.

1. **Fetch (명령 인출):** CPU는 **프로그램 카운터**(PC)가 가리키는 RAM 주소에서 기계어 명령어를 꺼내온다. 인출 직후 PC는 다음 명령어 주소로 순차 전진한다.
2. **Decode (명령 해독):** 제어 유닛(Control Unit)이 가져온 비트열을 해석하여 연산의 종류(`ADD`, `MOV` 등)와 피연산자 레지스터를 판별한다.
3. **Execute (명령 실행):** ALU가 연산을 수행하거나, 시스템 버스를 통해 RAM의 주소에 접근하여 데이터를 읽거나(`LOAD`) 쓴다(`STORE`).

CPU와 RAM은 3대 시스템 버스(주소 버스, 제어 버스, 데이터 버스)를 공유한다. 명령 인출(제어의 길)과 데이터 접근(저장의 길)은 동일한 버스 도로망을 사용하지만, **주소 버스에 누가 주소를 싣는가**(PC 레지스터인가, 명령어 내 데이터 주소인가)에서 출발점이 갈라진다.

## 제어문의 물리적 실체

고급 프로그래밍 언어의 `if`, `while`, `return` 같은 제어문은 하드웨어에 "조건문"이라는 별도의 전용 회로가 있어서 존재하는 것이 아니다.

하드웨어 수준에서 모든 조건 분기는 **PC 레지스터에 적힌 주소 값을 바꿀 것인가(Branch/Jump) 순차적으로 유지할 것인가**의 문제로 환원된다. ALU가 비교 연산을 수행한 뒤 상태 레지스터의 플래그(Zero, Sign 등)를 세우면, 제어 유닛은 그 플래그에 따라 PC 값을 점프 대상 주소로 덮어쓰거나 다음 주소로 흘려보낸다.

## 간접화의 대칭성: 데이터 포인터와 함수 포인터

메모리 주소를 다루는 간접 주소 지정(Indirect Addressing)은 저장 축과 제어 축 양쪽에서 대칭적인 추상화를 형성한다.

- **데이터 포인터:** **저장 축의 간접화**다. 변수가 값 자체가 아니라 다른 데이터가 있는 메모리 사물함의 주소를 가리킨다.
- **함수 포인터:** **제어 축의 간접화**다. 프로그램의 실행 흐름(PC)이 고정된 코드가 아니라 런타임에 결정되는 다른 코드 위치의 주소로 점프하도록 만든다.

## 제어 흐름과 상태 수명: 스택과 힙

세 축의 분리는 메모리 공간의 수명 관리 모델을 낳는다.

- **스택(Stack):** **제어 흐름과 저장 수명이 동기화된 공간**이다. 함수가 호출되면 스택 프레임이 할당되고, 제어가 반환(`return`)되어 복귀 주소로 PC가 돌아가는 즉시 해당 저장 공간의 수명도 함께 끝난다.
- **힙(Heap):** **제어 흐름으로부터 저장 수명을 탈동기화(독립)하기 위한 공간**이다. 함수의 실행이 끝나 제어가 다른 곳으로 이동해도 상태가 유지되어야 할 때 동적 할당을 사용한다. 제어 흐름과 저장 수명의 어긋남은 메모리 누수와 허상 포인터(Dangling Pointer)라는 문제를 유발한다.
