## 개요

[[멱등성]](idempotency)은 같은 논리적 작업을 여러 번 요청해도 정의된 범위에서 의도된 서버 효과가 한 번 수행한 것과 같아지는 성질이다. 여기서 “같다”는 물리적으로 코드가 한 번만 실행됐다는 뜻이 아니라, 관찰 가능한 논리 상태와 반환 결과가 중복 실행으로 부풀지 않는다는 뜻이다.

멱등성의 범위는 반드시 적어야 한다. 실용적인 논리 작업은 다음 요소의 묶음으로 표현할 수 있다.

`logical operation = namespace + key + parameter fingerprint + retention horizon + side-effect contract`

키가 같아도 namespace가 다르면 다른 작업일 수 있고, 같은 키를 다른 매개변수로 재사용하면 오류로 거부해야 할 수 있다. 보존 기간이 끝난 뒤에는 같은 문자열이 새 작업으로 해석될 수 있다.

## Exactly-once와의 경계

| 주장 | 멱등성으로 말할 수 있는가 |
|---|---|
| 같은 키·같은 매개변수의 재시도는 한 논리 효과로 수렴한다 | 정의된 namespace·보존 기간·저장 경계 안에서 가능 |
| 서버 함수가 물리적으로 한 번만 실행된다 | 멱등성만으로 보장하지 않음 |
| 데이터베이스 커밋과 외부 메일·결제가 한 원자 작업이다 | 별도의 통합·outbox·보상 계약이 필요 |
| 모든 시스템 경계를 넘어 global exactly-once다 | 기각해야 하는 과도한 일반화 |

HTTP의 멱등 메서드는 반복 요청의 의도된 효과를 규정하지만, 비멱등 API를 자동으로 안전하게 만들지는 않는다. Stripe의 idempotency key는 이 원칙을 API 범위에서 구현한 사례이며, FoundationDB의 unknown commit result는 데이터베이스 트랜잭션의 원자성과 외부 부작용의 원자성이 다름을 보여준다.

## 부분 실패와 unknown commit

호출자가 응답을 받지 못하면 요청이 서버에 도착하지 않았는지, 처리 중 실패했는지, 커밋 후 응답만 유실됐는지 즉시 알 수 없다. 이 상태에서 무조건 재시도하면 결제·메일·리소스 생성 같은 효과가 중복될 수 있고, 재시도하지 않으면 실제로 처리되지 않은 작업을 놓칠 수 있다.

멱등성은 이 불확실성을 없애는 마법이 아니라, 요청 식별자와 이전 결과를 저장해 재시도 판단을 안정화하는 계약이다. 따라서 key record의 동시 생성, parameter mismatch, TTL 만료, 진행 중 요청, 외부 부작용 전파를 구현 정책으로 명시해야 한다.

## 설계 점검표

1. key가 유일한 범위인 tenant·계정·리전·API 버전을 정의했는가.
2. 같은 key의 매개변수 fingerprint를 비교하고 불일치를 거부하는가.
3. 결과와 key record를 얼마 동안 보존하며, 늦은 재시도가 만료 뒤 새 작업이 되는가.
4. 처리 중 같은 key가 들어오면 대기·거부·재생 중 어떤 정책을 쓰는가.
5. 데이터베이스 커밋과 외부 부작용 사이의 atomicity gap을 어떻게 보상하는가.
6. 하위 서비스가 동일한 작업 식별자를 전달받고 각자의 중복 경계를 갖는가.
