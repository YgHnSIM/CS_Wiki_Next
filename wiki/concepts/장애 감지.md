## 개요

[[장애 감지]](failure detection)는 구성 요소가 실제로 고장났는지를 직접 관찰하는 기능이 아니라, heartbeat·timeout·요청 결과·trace·지연 분포에서 실패 가능성을 추정해 격리·재시도·복구 결정을 내리는 계층이다. 분산 시스템에서는 통신 지연과 정지 장애를 항상 구분할 수 없으므로 detector는 완전한 진실 oracle이 아니라 suspicion policy다.

## Completeness와 Accuracy

고전적인 failure detector의 질문은 모든 실제 고장을 결국 의심하는지(completeness), 정상 구성 요소를 고장이라고 의심하지 않는지(accuracy)로 나뉜다. 실제 운영에서는 두 조건을 동시에 완전하게 얻기 어렵다. threshold를 낮추면 탐지 지연이 줄지만 정상적인 tail latency를 장애로 볼 수 있고, threshold를 높이면 거짓 양성은 줄지만 격리가 늦어진다.

φ-accrual detector는 heartbeat 도착 분포에서 연속 suspicion 값을 계산해 이 선택을 threshold 정책으로 노출한다. 이는 고정 timeout보다 유연하지만, 어떤 threshold가 안전한지는 네트워크·스케줄러·부하·복구 비용에 의존한다.

## 서로 다른 실패 관찰

| 층 | 관찰 예 | 확정할 수 있는 것 | 확정할 수 없는 것 |
|---|---|---|---|
| liveness | heartbeat·health check | 특정 경로의 응답 부재·지연 | 모든 사용자 요청의 의미적 정상 |
| performance | p99·deadline·queue | 느림·기한 초과·자원 압박 | 프로세스가 완전히 죽었는지 |
| semantic | 오류 결과·잘못된 상태·trace | 특정 요청 경로의 결과 계약 위반 | 다른 경로·replica의 상태 |
| causal | retry·overload·recovery feedback | 장애가 자기 유지되는 경로의 단서 | 단일 threshold 조정만으로 회복되는지 |

Gray failure는 구성 요소가 일부 경로와 관찰자에게만 느리거나 잘못된 결과를 주는 상태다. Metastable failure는 부하·재시도·복구의 causal feedback이 상태를 자기 유지하는 경우를 가리킨다. 두 용어는 단순한 heartbeat timeout이나 모든 tail latency와 동의어가 아니다.

## 관측성의 역할

Trace와 span은 요청이 어느 경로를 지나 얼마나 걸렸는지, 재시도가 몇 번 발생했는지, 어느 하위 호출에서 결과가 바뀌었는지를 연결하는 계측 수단이다. 그러나 관측 데이터가 있다고 해서 detector가 semantic correctness를 자동으로 판정하지는 않는다. span status·exception·logical request·retry attempt의 의미를 먼저 정의해야 한다.

장애 감지 결과는 곧바로 사용자-facing 실패와 같지 않다. 감지된 구성 요소를 격리할지, 요청을 재시도할지, degraded result를 제공할지, 복구 후 stale state를 검증할지는 별도의 서비스 계약이다.
