## 분석 질문

“같은 소스로 빌드할 수 있다”는 문장은 충분하지 않다. [[Reproducible Builds - Definition]]은 소스 코드뿐 아니라 빌드 환경과 빌드 지침, 그리고 지정 산출물까지 정의해야 한다고 말한다. 따라서 이 분석은 빌드 결과의 동일성을 다음 질문으로 분해한다.

## 동일성의 층위

| 층위 | 판정 질문 | 대표적인 변동 |
|---|---|---|
| 소스 | 정확히 같은 revision·archive인가? | 이동하는 tag, 생성된 소스, submodule |
| 지침 | 같은 규칙과 명령을 실행하는가? | 숨은 flag, 설정 파일, target 선택 |
| 환경 | 결과에 영향을 주는 toolchain·의존성·변수를 고정했는가? | compiler/linker 버전, locale, timezone |
| 변동 입력 | 실행 시각·경로·순서·난수·네트워크를 통제했는가? | timestamp, directory order, build path, remote fetch |
| 산출물 | 무엇을 byte-by-byte 비교하는가? | 실행 파일, package, image와 log의 혼합 |
| 생성 경로 | 누가 어떤 builder와 입력으로 만들었다고 주장하는가? | provenance의 builder, parameters, dependencies |

이 표에서 앞의 다섯 층위는 재빌드와 산출물 비교의 계약이고, 마지막 층위는 provenance가 기록하는 실행 맥락이다. 둘은 서로 보완하지만 같은 판정이 아니다.

## 변동을 고정하는 방법과 비용

[[SOURCE_DATE_EPOCH Specification]]은 현재 시각을 기준 timestamp로 바꿔 시간 변동을 줄인다. [[Reproducible Builds - Definition]]과 관련 문서는 locale, 의존성 버전, 환경 변수와 같은 실제 영향 요소를 환경 정의에 포함할 수 있음을 보여준다. [[Bazel BUILD Files and Hermeticity]]는 알려진 입력과 제한된 I/O를 사용해 build graph 해석을 hermetic하게 만드는 구현 사례를 제공한다.

그러나 hermetic한 해석은 byte-by-byte 동일성의 충분조건으로 자동 승격할 수 없다. compiler가 backend나 target CPU를 다르게 선택할 수 있고, archive가 파일 순서를 기록할 수 있으며, 외부 네트워크 응답이나 작업 경로가 결과에 들어갈 수 있다. 따라서 구현 주장에는 실제 두 번의 빌드와 hash·byte 비교, 차이 위치 조사 기록이 필요하다.

## Reproducible build와 provenance의 경계

| 질문 | 재현 가능한 빌드 | provenance |
|---|---|---|
| 무엇을 확인하는가? | 지정 산출물이 bit-by-bit 같은가 | 산출물이 어떤 builder·입력·실행에서 나왔는가 |
| 핵심 행위 | 독립된 환경에서 재빌드하고 비교 | attestation을 생성·서명·검증 |
| 강점 | 빌드 결과의 동일성 및 일부 변조 탐지 | 생성 경로, 의존성, 실행 맥락의 추적 |
| 남는 위험 | 비교 범위 밖 산출물·미기록 환경·비교 불능 도구 | 거짓·불완전한 입력 기록, 동일성 자체의 미검증 |

SLSA v1.2는 provenance가 산출물을 추적하고 다른 사람이 다시 빌드하도록 도울 수 있다고 설명하며, `buildDefinition`, `runDetails`, `builder`, `resolvedDependencies`를 구분한다. 동시에 이 기록은 “어떻게 만들어졌다고 attest하는가”를 제공한다. 실제 동일성은 해당 정의로 재빌드한 결과를 별도로 비교해야 한다는 것이 이 조사에서의 결론이다.

## 기존 AI 문서와의 중복 경계

이 pair는 [[AI 컴퓨팅 병목]], [[계산-통신 중첩]], [[메모리 이동과 병목 이동]]과 중복되지 않는다. 기존 문서가 실행 중 처리량·대기·메모리·통신 병목이 어디로 이동하는지 다룬다면, 이 pair는 소스에서 배포 산출물까지의 빌드 결과가 동일한지와 그 생성 경로를 다룬다. AI 모델을 빌드하더라도 질문은 runtime 병목이 아니라 artifact identity와 build trust boundary다.

## 다음 조사로의 연결

다음 pair인 dependency provenance/registry에서는 `resolvedDependencies`의 URI·digest·registry와 lockfile의 역할을 좁혀 조사한다. 그 뒤 StableHLO·MLIR·ABI는 같은 소스가 아니라 중간 표현과 호출 규약이 호환성 경계를 어떻게 만드는지 분석하고, runtime contract는 실행 시 입력·상태·오류·성능 보장을 명시하는 방향으로 이어진다.

## 미해결 사항

- 서로 다른 CPU·OS·compiler backend 사이에서 어떤 동일성 수준을 요구할지 저장소 차원에서 결정하지 않았다.
- 네트워크를 차단하거나 모든 fetched artifact를 digest로 고정하는 구현 검증은 이 pair의 문서 작성과 별도다.
- provenance의 완전성, signer-builder 신뢰 관계, 독립 재빌드 플랫폼 수는 다음 provenance pair에서 심화한다.
