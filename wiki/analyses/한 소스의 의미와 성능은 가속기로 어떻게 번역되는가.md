## 핵심 주장

하나의 [[소스 프로그램]]이 가속기에서 빠르게 실행된다는 말에는 적어도 두 개의 약속이 들어 있다. 첫째, 입력·출력·오류·수치 정확성에 관한 프로그램의 의미를 요구한 수준에서 유지해야 한다. 둘째, 그 의미를 표현하는 계산을 대상 장치의 연산기·메모리·병렬 단위에 맞게 배치해 실제 시간, 처리량 또는 에너지 비용을 개선해야 한다.

이 두 약속은 같은 번역 단계에서 자동으로 해결되지 않는다. [[LLVM - A Compilation Framework for Lifelong Program Analysis and Transformation|LLVM]]은 분석과 변환을 이어 갈 공통 표현을, [[Scalable Parallel Programming with CUDA|CUDA]]는 가속기 병렬성·메모리 공간을 드러내는 실행 모델을, [[Decoupling Algorithms from Schedules for Easy Optimization of Image Processing Pipelines|Halide]]는 계산 정의와 실행 배치의 분리를, [[TVM - An Automated End-to-End Optimizing Compiler for Deep Learning|TVM]]은 그래프·연산자·대상별 자동 탐색의 결합을 각각 보여 준다.

따라서 성능 이식성은 “한 소스가 모든 장치에서 같은 속도로 실행된다”는 성질이 아니다. **같은 결과 계약을 유지하면서, 각 대상에 맞는 여러 실행 후보를 만들고, 그 후보를 같은 측정 경계에서 비교·선택할 수 있는 능력**이다.

## 번역 사슬

| 층위 | 고정하거나 표현할 것 | 대표 자료 | 실패하면 생기는 혼동 |
|---|---|---|---|
| 의미 계약 | 입력·출력, 허용 오차, 예외, 관찰 가능한 부작용 | [[IEEE 754-2019 Standard for Floating-Point Arithmetic]] | 더 빠른 코드가 다른 결과를 내도 같은 계산이라고 부른다. |
| 중간 표현 | 제어·데이터 흐름, 형식, 계산 그래프와 연산자 구조 | [[LLVM - A Compilation Framework for Lifelong Program Analysis and Transformation]], [[TVM - An Automated End-to-End Optimizing Compiler for Deep Learning]] | 프런트엔드 의미와 백엔드 제약을 한 덩어리로 취급해 변환 범위를 설명하지 못한다. |
| 스케줄과 배치 | 타일링, 융합, 재계산, 벡터화, 병렬 단위, 데이터 배치 | [[Decoupling Algorithms from Schedules for Easy Optimization of Image Processing Pipelines]], [[TVM - An Automated End-to-End Optimizing Compiler for Deep Learning]] | 알고리즘의 산술량만으로 장치별 실행 시간을 설명하려 한다. |
| 코드 생성과 실행 | 대상 명령, 장치 메모리, 커널·모듈, 런타임 호출과 동기화 | [[Scalable Parallel Programming with CUDA]], [[TVM - An Automated End-to-End Optimizing Compiler for Deep Learning]] | 호스트·장치 경계와 데이터 이동을 계산 밖의 비용으로 빼 버린다. |
| 측정 계약 | 작업 부하, 장치·버전, 탐색 예산, 시간·처리량·에너지 분모 | [[TVM - An Automated End-to-End Optimizing Compiler for Deep Learning]] | 특정 모델·장치의 속도 배수를 모든 가속기의 보편적 이점으로 일반화한다. |

이 사슬의 앞쪽은 “무엇을 계산하는가”를, 뒤쪽은 “어떻게 실행하는가”를 다룬다. 앞쪽이 비어 있으면 빠른 결과가 원래 요구를 만족하는지 판단할 수 없고, 뒤쪽이 비어 있으면 같은 계산이라도 왜 한 대상에서만 빠른지 설명할 수 없다.

## 1. 중간 표현은 의미와 기계를 분리하지만 둘을 단절하지 않는다

[[LLVM - A Compilation Framework for Lifelong Program Analysis and Transformation|LLVM]]의 SSA 기반 표현은 프런트엔드가 해석한 프로그램 구조를 분석·최적화·코드 생성 단계가 공유하게 한다. 이로써 언어별 표기와 기계별 명령 선택 사이에 변환 가능한 공간이 생긴다. 링크 시점과 실행 시점의 정보를 정적 변환과 연결할 수 있다는 점도 중요하다.

그러나 중간 표현 자체가 프로그램 의미를 완전히 대리하지는 않는다. LLVM 논문은 특정 객체 모델·런타임·메모리 안전성을 강제하지 않으며, 고수준 언어 특성을 모두 직접 표현하려는 보편 IR도 아니다. 소스 언어의 정의된 동작, 외부 호출, 예외, 수치 규칙을 어느 단계에서 어떤 조건으로 낮출지는 여전히 컴파일러와 런타임의 계약이다.

[[TVM - An Automated End-to-End Optimizing Compiler for Deep Learning|TVM]]은 이 점을 딥러닝에 맞게 넓힌다. 계산 그래프는 연산자 사이 의존성과 큰 텐서의 구조를 보존해 융합·상수 접기·메모리 계획에 쓰이고, 연산자 표현과 저수준 루프는 장치별 코드 생성과 스케줄 탐색에 쓰인다. 하나의 IR로 모든 최적화를 설명하기보다, 목적에 맞는 여러 표현 사이의 변환을 관리하는 방식이다.

## 2. 스케줄은 알고리즘의 부수적 구현 세부가 아니다

[[Decoupling Algorithms from Schedules for Easy Optimization of Image Processing Pipelines|Halide]]는 계산 함수가 정한 결과와, 그 함수를 어느 순서·공간·병렬 단위에서 계산할지를 분리했다. 이 관점에서 타일링, 융합, 재계산, 벡터화, 병렬화는 소스 알고리즘을 다시 작성하지 않고 교체할 수 있는 실행 후보가 된다.

[[TVM - An Automated End-to-End Optimizing Compiler for Deep Learning|TVM]]은 이 분리를 고정된 손작업 튜닝으로 끝내지 않는다. 그래프 수준의 연산자 융합과 연산자 수준의 텐서 스케줄을 함께 다루고, 비용 모델로 후보 탐색을 유도한다. 여기서 자동 탐색이 하는 일은 “가장 빠른 코드”를 추상적으로 발견하는 것이 아니라, 지정된 장치·입력 형태·소프트웨어 버전·탐색 예산 아래의 후보 집합에서 실행을 선택하는 것이다.

따라서 스케줄은 성능 계약의 일부다. 같은 알고리즘이라도 어떤 중간값을 저장했는지, 어떤 순서로 재결합했는지, 데이터 이동을 줄이려고 어느 연산을 융합했는지에 따라 메모리 사용량·병렬성·지연이 달라진다. 이를 소스 코드 바깥의 사소한 구현 차이로 남기면 결과를 재현하거나 다른 장치에 옮길 수 없다.

## 3. 가속기 실행 모델은 병렬성과 데이터 이동을 함께 노출한다

[[Scalable Parallel Programming with CUDA|CUDA]]는 호스트와 장치, 커널과 스레드 계층, 여러 메모리 공간을 분리해 GPU의 실행 모델을 프로그램에 드러낸다. 이 모델은 작업을 코어 수가 다른 GPU에 확장할 길을 제공하지만, 동시에 데이터 배치·스레드 구성·메모리 접근이 성능의 핵심 조건임을 보여 준다.

가속기에서 빠른 산술 연산은 종단 성능의 한 요소일 뿐이다. 장치로 보낼 작업이 충분한지, 입력과 중간값을 얼마나 옮기는지, 병렬 단위가 얼마나 균등한지, 장치 메모리 안에서 재사용이 가능한지, 호스트와의 동기화가 어느 지연을 추가하는지가 함께 결과를 만든다. 이기종 실행 모델은 이 선택을 숨기는 대신, 코드 생성과 런타임이 명시적으로 다룰 수 있게 한다.

이는 [[도메인 특화 가속기]]의 범용성·효율 교환과도 연결된다. 하드웨어가 특정 연산·정밀도·데이터 경로에 자원을 집중할수록, 상위 스택은 그 특성을 실제 작업에 맞게 호출·배치·검증해야 한다. 그렇지 않으면 높은 최고 연산률은 데이터 이동이나 작은 작업, 지원하지 않는 연산에서 유휴 자원으로 남을 수 있다.

## 4. 같은 결과의 범위를 먼저 정해야 한다

스케줄과 코드 생성은 연산 순서, 중간 저장, 데이터 형식과 병렬 재결합을 바꿀 수 있다. 특히 부동소수점에서는 수학적으로 같은 식도 재결합 순서·중간 정밀도에 따라 다른 비트와 예외를 낼 수 있다. [[IEEE 754-2019 Standard for Floating-Point Arithmetic]]은 지정한 산술 연산의 공통 규칙을 제공하지만, 임의의 최적화·병렬화가 전체 프로그램의 비트 동일성을 보장하지는 않는다.

그러므로 가속기의 성능을 보고할 때는 결과 계약을 먼저 써야 한다. 비트 동일성인지, 정해진 허용 오차 안의 수치 동일성인지, 과업 품질 문턱을 만족하면 되는지에 따라 허용되는 융합·재결합·저정밀도 사용이 달라진다. 결과 계약이 바뀐 최적화는 단순한 가속이 아니라 정확성·자원 효율의 교환으로 비교해야 한다.

## 최소 비교 형식

한 소스의 성능 이식성을 검토할 때는 다음 다섯 묶음을 함께 남긴다.

1. 계산과 결과: 모델·알고리즘, 입력 형태와 크기, 출력의 정확성·품질 기준을 기록한다.
2. 표현과 변환: 사용한 중간 표현, 그래프 재작성, 융합·타일링·배치·벡터화와 탐색 예산을 기록한다.
3. 대상과 런타임: 장치, 메모리 용량, 드라이버·컴파일러·라이브러리 버전, 호스트·장치 경계를 기록한다.
4. 작업 부하와 지표: 배치, 동시성, 워밍업, 시간·처리량·꼬리 지연·에너지 가운데 무엇을 잴지 정한다.
5. 기준 구현: 수작업 튜닝, 공급업체 라이브러리, 이전 컴파일러와 무엇을 같은 조건에서 비교했는지 밝힌다.

이 형식은 모든 대상에서 같은 절대 속도를 요구하지 않는다. 대신 같은 계산이 서로 다른 대상에서 어떤 변환과 자원을 통해 어느 비용으로 실행되는지, 그리고 그 차이가 결과 계약을 지키는지를 검토 가능하게 만든다.
