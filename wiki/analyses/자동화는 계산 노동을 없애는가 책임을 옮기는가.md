## 문제 제기

자동화가 “사람의 일을 대체한다”는 말은 무엇을 일로 세는지에 따라 달라진다. 계산 공장의 작업 분해, Fortran의 자동 번역, 라이브러리·API의 재사용, AI 코딩 지원은 모두 일부 반복 작업의 비용을 낮췄지만, 문제를 정의하고 결과를 확인하며 예외를 처리하고 다른 사람·시스템과 통합하는 일을 자동으로 없애지는 않았다.

따라서 자동화의 효과를 평가할 때는 산출량이나 완료 시간 하나보다 **어떤 작업 단위가 도구로 옮겨졌고, 어떤 판단과 결과 계약이 사람에게 남았는가**를 먼저 물어야 한다.

## 작업의 이동: 외주화의 역사적 단계와 남는 책임

자동화의 역사는 인간 정신의 유한성을 보완하기 위해 인지적 부담을 외부 기호와 도구로 넘겨온 다층적 외주화의 과정이다.

1. **기억의 외주화**: 17세기 [[토머스 홉스]](Thomas Hobbes)는 인간 사고의 휘발성과 망각을 극복하기 위해 물리적 부호인 '표지(Nota)'를 고안했다([[Elementorum Philosophiae Sectio Prima De Corpore]]). 이 단계에서는 인간의 내적 사념을 외부 매체에 고정하여 보존하는 것이 핵심이었다.
2. **연산의 외주화와 분업화**: [[인간 계산자와 계산 공장]]에서 대규모 계산이 작업표와 분업화된 전달 규칙으로 조직되었듯, [[고트프리트 빌헬름 라이프니츠]](Gottfried Wilhelm Leibniz)의 [[보편 기호법과 사유의 계산|사유의 계산(Calculus Ratiocinator)]]과 [[맹목적 사고와 기호적 인식|맹목적 사고]]([[Meditationes de Cognitione, Veritate et Ideis]])에서 정초되어, [[The FORTRAN Automatic Coding System|컴파일러]]의 자동 번역과 [[수학 표에서 스프레드시트로|스프레드시트]]의 재계산으로 실체화된 단계다. 인간은 기호 간의 형식적 관계와 규칙만을 선언하고, 구체적인 기호 변환과 계산 실행은 기계 엔진에 전담시켰다.
3. **의미 구성의 외주화**: 현대 트랜스포머 기반 거대언어모델(LLM)과 생성형 AI에 이르러서는 단순 기호 변환을 넘어, 자연어 문장이나 코드 초안과 같은 지적 표현의 합성 자체를 기계에 위임하는 단계로 확장되었다([[홉스와 라이프니츠, 기호에서 AI까지]]).

그러나 [[존 설]](John Searle)의 [[중국어 방과 구문-의미 간극|중국어 방(Chinese Room)]] 논증([[Minds, Brains, and Programs]])이 통찰하듯, 기계가 수행하는 작업은 고도화된 확률적 패턴 변환일 뿐 본질적으로 형식적 기호 조작(구문론, syntax)에 머문다. 기계는 생성된 코드가 실제 저장소와 비즈니스 맥락에서 갖는 의미(semantics)를 이해하지 못한다.

기계가 구문론적 기호 처리를 대행할수록, 생성된 제안의 의미론적 맥락을 확인하고 타당성을 시험하는 [[검증 노동]]과 실패 시 책임을 떠안는 [[자동화 경계]]의 획정은 오히려 더욱 온전히 인간의 몫으로 남는다.

| 시대·도구 | 외주화 단계 | 주로 줄이는 작업 | 새로 중요해지거나 남는 작업 |
|---|---|---|---|
| 기호·표지 (홉스) | 기억의 외주화 | 망각 방지, 개인 사념 보존 | 표지의 일관성 유지, 사회적 신호 규약화 |
| 계산 조직·수학 표 | 연산의 분업화 | 반복 산술의 개별 수행 | 작업 분해, 전달, 검산, 오류 추적 |
| 컴파일러·스프레드시트 | 연산의 외주화 | 기계 명령 작성, 반복 재계산 | 형식 규칙 선언, 모형 타당성, 디버깅 |
| 재사용·API | 모듈 외주화 | 재구현과 탐색의 일부 | 인터페이스 이해, 버전·호환성, 조합 |
| AI 코딩 지원 | 의미 구성의 외주화 | 초안 작성·검색·반복 구현의 일부 | 맥락 해석, 의미론적 제안 검증, [[검증 노동]], 책임 귀속 |

## 생산성 수치를 읽는 계약

[[The Impact of AI on Developer Productivity: Evidence from GitHub Copilot]]은 경계가 분명한 JavaScript 구현 과제에서 Copilot 접근 집단이 더 빨리 완료한 결과를 보고한다. 반면 [[Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity]]은 익숙한 대형 오픈소스 저장소의 실제 이슈에서 초기 2025년 도구 사용이 허용된 과제가 더 오래 걸렸다고 보고한다. 두 결과는 어느 하나가 다른 하나를 무효화하는 모순이 아니라, 작업·개발자·도구·완료 기준이 다른 측정이다.

| 비교 차원 | 독립 구현 과제 실험 | 친숙한 실제 저장소 연구 |
|---|---|---|
| 작업 | JavaScript HTTP 서버 구현 | 버그 수정·기능·리팩터링 이슈 |
| 맥락 | 비교적 경계가 분명한 과제 | 장기 기여자가 아는 대형 저장소 |
| 성공 기준 | 과제 완료 시간 | 사람이 만족할 PR, 테스트·문서·스타일 포함 |
| 해석 | 해당 과제에서의 시간 효과 | 해당 시점·도구·개발자 집단에서의 시간 효과 |

[[Expectation vs. Experience: Evaluating the Usability of Code Generation Tools Powered by Large Language Models]]은 도구 선호, 완료 시간·성공률, 생성 코드의 이해·편집·디버깅이 서로 다른 관찰 대상임을 보인다. [[The SPACE of Developer Productivity]] 역시 개발 성과를 활동량 하나가 아니라 만족·성능·활동·협업·효율·흐름의 여러 차원으로 본다.

## 책임을 옮기는 자동화

자동화가 안전하고 유용한 결과를 만들려면, 생성 단계와 검증 단계를 하나의 성과로 합치지 않아야 한다. 다음 네 가지를 분리하면 “더 빨리 만들었다”는 말의 범위를 명확히 할 수 있다.

1. **표현:** 사람의 의도를 어떤 입력·제약·문맥으로 도구에 전달했는가.
2. **생성:** 도구가 어떤 코드·설계·테스트 후보를 제안했는가.
3. **검증:** 누가 어떤 테스트·리뷰·정적 분석·운영 관찰로 결과 계약을 확인했는가.
4. **귀속:** 실패·보안 문제·유지보수 비용이 생겼을 때 누가 수정·설명·중단을 결정하는가.

이 틀은 AI 코딩 지원이 생산성을 높인다거나 낮춘다는 결론을 미리 정하지 않는다. 대신 어떤 사람이, 어떤 과제를, 어떤 도구와 검증 체계로, 어떤 결과 기준 아래 수행했는지를 남겨 비교 가능한 질문으로 바꾼다.
