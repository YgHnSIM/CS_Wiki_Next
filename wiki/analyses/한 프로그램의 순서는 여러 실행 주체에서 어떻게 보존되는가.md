## 문제 제기

[[구조적 프로그래밍]]은 하나의 프로그램 안에서 실행 위치와 상태 변화를 사람이 추적할 수 있는 제어 구조로 정리했다. 그러나 프로그램이 여러 실행 주체로 나뉘어 공유 상태를 함께 다루기 시작하면 “다음 명령”이라는 표현만으로는 충분하지 않다. 각 실행 주체에는 자기 제어 흐름이 있고, 전체 시스템에는 이 흐름들이 만나는 공유 상태·대기·관찰의 경계가 생긴다.

이 분석은 단일 프로그램의 순서가 하나의 보장으로 확장되는 것이 아니라, 서로 다른 단위에서 세 종류의 계약으로 분화된다고 본다.

1. **접근 순서:** 누가 같은 임계 구역에 동시에 들어갈 수 있는가.
2. **메모리 관찰 순서:** 여러 프로세서의 읽기·쓰기가 어떤 전역 순서로 보이는가.
3. **객체 결과 순서:** API 연산이 외부에서 어느 한 순간에 일어난 것처럼 보이고, 실제 시간의 선후관계를 지키는가.

## 단일 제어 흐름에서 공유 상태로

한 순차 프로그램에서는 제어 위치, 호출 깊이, 반복 횟수처럼 프로그램 내부의 구조가 실행 진행을 설명한다. [[동시성]]에서는 여러 실행 주체가 각자 이런 내부 순서를 가지면서, 서로의 속도·중단·관찰에 영향을 준다. 따라서 정확성은 한 실행 경로가 잘 구성됐는지뿐 아니라, 가능한 실행 끼어들기(interleaving) 전체에서 어떤 결과가 허용되는지를 말해야 한다.

[[Cooperating Sequential Processes]]는 이 변화의 초기 형태를 보여 준다. 두 프로세스가 공유 변수를 확인하고 갱신하는 순서가 다르면 둘 다 임계 구역에 들어갈 수 있다. [[Monitors: An Operating System Structuring Concept]]은 이 문제를 지역 상태, 접근 절차, 조건 대기를 묶는 모듈 경계로 옮긴다. 즉, 제어 구조는 개별 프로그램의 가독성만이 아니라 공유 자원에 대한 접근 규칙을 어디에 둘 것인가의 문제가 된다.

## 세 순서 계약

| 계약 | 단위 | 보존해야 할 것 | 대표 질문 | 직접 보장하지 않는 것 |
|---|---|---|---|---|
| 상호 배제·동기화 | 임계 구역·조건 대기 | 허용되지 않은 동시 진입 방지와 조건별 진행 | 누가 언제 공유 자원을 바꿀 수 있는가 | 모든 메모리 연산의 전역 순서, 모든 요청의 완료 |
| 순차 일관성 | 메모리 읽기·쓰기 | 프로세서별 프로그램 순서와 하나의 전역 순서 | 어떤 읽기가 어떤 쓰기를 관찰할 수 있는가 | 객체 호출의 실제 시간 순서, API의 서비스 지연 |
| 선형화 가능성 | 객체의 호출·응답 이력 | 순차 명세와 겹치지 않은 연산의 실제 시간 순서 | 이 `enqueue`·`withdraw`는 언제 효과가 났는가 | 복제·장애·처리량·공정성의 구현 정책 |

이 표의 행들은 약한 것에서 강한 것으로 단순히 정렬되지 않는다. 서로 다른 관찰 단위와 문제를 가진다. 한 시스템이 모니터로 임계 구역을 보호해도 메모리 모형의 조건이 필요할 수 있고, 순차 일관적 메모리 위에서도 객체 API가 어떤 호출·응답 이력을 약속하는지는 별도 명세가 필요하다.

## 같은 예시를 다른 단위로 읽기

공유 큐에 한 실행 주체가 `enqueue(x)`를 수행하고 다른 실행 주체가 `dequeue()`를 수행하는 상황을 생각할 수 있다.

- **상호 배제**는 큐의 내부 상태를 바꾸는 임계 구역에 두 실행 주체가 동시에 들어가 연결 구조를 깨지 않게 한다.
- **순차 일관성**은 큐 구현에 쓰인 메모리 읽기·쓰기가 각 프로세서의 프로그램 순서와 양립하는 하나의 전역 순서로 관찰되게 한다.
- **선형화 가능성**은 `enqueue(x)`의 응답이 끝난 뒤에 `dequeue()`가 시작했다면, 그 `dequeue()`를 빈 큐처럼 해석할 수 없게 하는 객체 수준의 실제 시간 계약을 제공한다.

이 예시는 순차 일관성이 불필요하다는 뜻도, 선형화 가능성이 언제나 필요한 API 계약이라는 뜻도 아니다. 어떤 단위에서 어떤 결과를 약속할지 먼저 정해야 구현·검증·성능 비교의 대상이 선명해진다는 뜻이다.

## 구현 경계와 성능 경계

공유 상태의 순서를 보존하려면 대기·통신·메모리 동기화·재시도가 생길 수 있다. 하지만 이 비용을 “동시성의 비용” 하나로 합치면 무엇을 최적화했는지 알 수 없다.

- 임계 구역의 대기는 공유 자원 접근 정책과 작업 부하에 좌우된다.
- 메모리 순서의 구현 비용은 프로세서·캐시·컴파일러·동기화 원시 연산의 조합에 좌우된다.
- 객체 결과의 비용은 자료 구조, 복제 범위, 트랜잭션, 실패 모형과 외부 부작용의 처리에 좌우된다.

[[병렬 확장성]]의 성능 수치와 [[복제 로그와 합의]]의 상태 순서를 비교할 때는 이 층들을 분리해야 한다. 복제 로그가 명령 순서를 맞춘다는 사실은 특정 API가 모든 실패·재시도·외부 부작용에서 선형화 가능하다는 주장과 같지 않으며, 강한 객체 계약이 곧 좋은 꼬리 지연을 뜻하지도 않는다.

## 다음 연결의 기준

이 분석은 P8의 네트워크·RPC·분산 저장 확장을 위한 중간 기준이다. 로컬 공유 메모리의 읽기·쓰기, 한 프로세스 안의 모니터, 여러 노드의 복제 로그는 모두 순서를 다루지만, 통신 지연·부분 실패·재시도·중복 부작용이 추가되면 보존해야 할 단위가 다시 달라진다. 다음 단계에서는 “로컬 호출처럼 보이는 요청”이 언제 원격 상태 변경의 결과 계약이 되는지 별도로 다뤄야 한다.

## 결론

한 프로그램의 순서는 여러 실행 주체로 넓어질 때 사라지지 않는다. 대신 **접근**, **메모리 관찰**, **객체 결과**의 서로 다른 계약으로 나뉜다. 상호 배제와 동기화는 누가 상태를 바꿀 수 있는지, 순차 일관성은 읽기·쓰기가 어떤 순서로 보이는지, 선형화 가능성은 외부 연산 이력이 어떤 실제 시간 순서를 지키는지를 각각 말한다.

따라서 동시 시스템을 설명하거나 평가할 때는 “일관성이 있다” 또는 “락을 쓴다”라고 끝내지 말고, 다음을 함께 밝혀야 한다.

`대상 단위 + 보존할 순서 + 진행·실패 조건 + 구현 경계 + 측정 지표`

이 다섯 항목이 있어야 구조적 제어 흐름에서 멀티코어와 분산 상태까지 이어지는 순서 문제를 같은 말로 뭉개지 않고 비교할 수 있다.
