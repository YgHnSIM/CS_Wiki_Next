## 핵심 주장

[[하드웨어 실행 모델은 어떻게 제어와 상태를 엮는가]]는 컴퓨터의 물리적 하드웨어 제약이 어떻게 프로그래밍 언어의 제어 구조, 포인터 간접화, 메모리 수명 관리 모델을 필연적으로 형성했는지를 추적하는 분석이다.

컴퓨터의 실행은 연산(ALU)과 저장(RAM)이라는 공간적 분리만으로 완성되지 않는다. 1843년 [[에이다 러브레이스]]가 "자카드 직조기가 꽃과 잎을 짜듯, 해석 기관은 대수적 패턴을 짠다"고 갈파했듯, **프로그램 카운터(PC)라는 제어의 바늘이 날실(저장)과 씨실(연산) 사이를 오가며 명령 인출과 데이터 접근을 직조**할 때 비로소 프로그램의 실행이 성립한다. 고수준 언어의 조건문, 함수 포인터, 콜 스택과 힙 동적 할당은 모두 이 3축의 물리적 한계와 버스 공유 구조를 다루기 위해 고안된 소프트웨어적 해법이다.

## 계층별 전환

| 층위 | 하드웨어 물리 메커니즘 | 소프트웨어 추상화 | 핵심 해결 과제 |
|---|---|---|---|
| **실행 축 분리** | ALU(레지스터 계산) vs RAM(바이트 셀) vs PC(순차/분기) | 변수의 메모리 상주와 레지스터 표현식 평가 | 회로 재배선 없이 임의의 계산 절차 수행 |
| **통신과 버스** | 단일 시스템 버스 공유 (명령 Fetch vs 데이터 LOAD/STORE) | 폰 노이만 병목, 캐시 계층, 메모리 보호 구역 | 단일 도로망에서 제어 신호와 데이터 화물의 충돌 완화 |
| **제어 전이** | PC 레지스터 주소 덮어쓰기 (Jump / Branch) | 조건문(`if`, `while`), 구조적 제어 블록, 함수 반환 | 전용 조건 회로 없이 복잡한 분기 논리 구성 |
| **간접화** | 주소 버스를 통한 간접 주소 지정 (Indirect Addressing) | 데이터 포인터(저장 간접화), 함수 포인터(제어 간접화) | 컴파일 시점에 확정할 수 없는 동적 상태·경로 접근 |
| **수명 관리** | 스택 포인터(`RSP`) 증감 vs 힙 관리자(`brk`, `mmap`) | 스택 프레임(제어 동기화) vs 힙(제어 탈동기화) | 제어 흐름의 종료 후에도 보존되어야 하는 상태 관리 |

## 분석

### 1. 3축 분리와 ALU의 물리적 제약

하드와이어드 컴퓨터(ENIAC 등)는 연산 논리와 저장 데이터가 물리적 배선으로 뒤엉켜 있었다. [[First Draft of a Report on the EDVAC]]가 제안한 저장 프로그램 방식은 연산(CPU)과 저장(RAM)을 물리적으로 영구히 갈라놓았다.

이 분리는 완전한 프로그래밍 유연성을 제공했지만, 동시에 **ALU는 레지스터에 올라온 값만 직접 계산할 수 있다**는 물리적 제약을 만들었다. RAM의 값은 반드시 `LOAD`를 거쳐 레지스터로 복사된 뒤 연산되고, 결과는 다시 `STORE`로 RAM에 쓰인다. C 언어의 변수가 “RAM에 거주하며 연산 시 레지스터로 출근하는 값”이 되는 이유가 바로 이 하드웨어 분업 구조에 있다.

### 2. 제어문의 환원과 PC 레지스터

하드웨어에는 `if`, `while`, `return`을 처리하는 마법 같은 "조건문 회로"가 따로 존재하지 않는다. 모든 고수준 제어 흐름은 **ALU 연산 결과 플래그(Zero, Sign, Overflow 등)를 검사하여 PC 레지스터에 적힌 주소를 바꿀 것인가(Branch/Jump) 유지할 것인가**의 물리적 선택으로 환원된다.

초기 컴퓨터의 점프는 프로그래머가 이 PC 조작을 날것 그대로 다루는 형태였다. 그러나 무제한 점프는 실행 좌표를 잃어버리게 만들었고, Dijkstra의 [[A Case against the GO TO Statement]]와 [[Structured Programming]]은 이 기계 점프를 블록 구조(`if-else`, `while`) 안에 가두어 인간이 추적 가능한 텍스트 구조로 정립했다.

### 3. 간접화의 대칭성: 데이터 포인터 vs 함수 포인터

주소(Address)는 메모리 셀의 고유 번호다. 이 번호를 주소 버스에 실어 간접적으로 대상을 참조하는 메커니즘은 저장 축과 제어 축에서 대칭적으로 작동한다.

- **저장 축의 간접화 (데이터 포인터):** 주소 버스에 실린 번호가 데이터 영역을 가리킬 때, 프로그램은 고정된 변수 이름 대신 런타임에 결정된 메모리 칸을 읽고 쓴다.
- **제어 축의 간접화 (함수 포인터):** 주소 버스에 실린 번호가 코드 영역의 명령어 시작 번지를 가리키고 이를 PC에 적재할 때, 프로그램은 런타임에 결정된 실행 경로로 제어를 넘긴다.

두 간접화는 모두 하드웨어의 간접 주소 지정 메커니즘을 소프트웨어 수준에서 얇게 노출한 결과다.

### 4. 제어와 수명의 동기화(스택)와 탈동기화(힙)

함수 호출이 발생하면 [[복귀 주소]]가 보존되고 새로운 프레임이 할당된다. 이 공간이 [[스택]]이다. 스택의 본질은 **제어 흐름과 저장 수명이 완벽하게 동기화되어 있다**는 점이다. 함수가 복귀하여 제어가 호출자로 돌아가면, 그 함수의 로컬 변수 칸은 즉시 유효성을 잃는다.

반면, 어떤 데이터는 제어 흐름이 함수를 빠져나간 뒤에도 살아남아야 한다. 이를 위해 하드웨어 실행 모델은 제어 흐름으로부터 저장 수명을 **탈동기화**(독립)한 영역인 힙(Heap)을 필요로 한다. 그러나 제어와 저장이 분리되는 순간, “언제 메모리를 반환할 것인가”라는 책임이 발생하며, 이는 메모리 누수(Leak), Use-After-Free(UAF), 댕글링 포인터 같은 현대 시스템 프로그래밍의 핵심 결함으로 이어진다.

## 의미

[[하드웨어 실행 모델]]의 3축 구조를 파악하는 것은 컴퓨터 구조와 프로그래밍 언어 런타임 사이의 추상화 층위를 명확히 이해하는 기반이 된다. 고급 언어의 구문과 메모리 모델은 추상적인 규칙의 집합이 아니라, 물리적 하드웨어의 연산·저장·제어 한계를 가장 효율적이고 안전하게 제어하기 위해 진화해 온 결과다.
