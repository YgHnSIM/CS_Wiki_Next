## 문제 제기

네트워크가 응답을 잃었을 때 클라이언트는 같은 요청을 다시 보내야 할지 결정해야 한다. 하지만 서버가 이미 효과를 적용했는지 알 수 없다면, 재시도는 누락을 줄이는 동시에 중복 효과를 만들 수 있다. “이 시스템은 exactly once다”라는 문장은 이 불확실성을 어느 경계까지 해결했는지 밝히지 않으면 검증할 수 없다.

## 논리적 한 번과 물리적 여러 번

멱등성은 동일한 논리 작업의 반복 요청이 관찰 가능한 효과를 한 번 수행한 것과 같아지도록 만든다. 내부 함수가 두 번 실행되거나 메시지가 여러 번 전달되는 것을 금지하는 개념이 아니다. 중요한 것은 중복 실행을 결과에 반영하지 않거나, 동일한 결과를 재사용할 수 있는 상태 계약이다.

| 경계 | 필요한 계약 | 실패 시 남는 문제 |
|---|---|---|
| API endpoint | key·namespace·parameter fingerprint | 같은 key의 다른 작업 충돌 |
| key store | 동시 생성·결과 저장·TTL | 늦은 재시도가 새 작업이 됨 |
| database transaction | commit/abort와 retry 단위 | commit unknown 뒤 중복 갱신 |
| message pipeline | producer·consumer transaction 범위 | 외부 DB·메일과 atomicity gap |
| 외부 부작용 | idempotent API·outbox·compensation | 결제·메일·파일의 중복 또는 누락 |

각 층의 경계를 넘어갈 때는 “한 번”이 자동으로 전파되지 않는다. Kafka나 Raft 같은 내부 로그·상태 기계의 순서 보장도 임의의 외부 API 호출이나 결제 효과의 중복 제거를 대신하지 않는다.

## Unknown commit의 시간선

1. 클라이언트가 작업 key를 보내고 서버가 트랜잭션을 시작한다.
2. 서버가 데이터베이스에 커밋했지만 응답을 보내기 전에 네트워크가 끊긴다.
3. 클라이언트는 `committed`와 `not committed`를 구분하지 못한 채 재시도를 고려한다.
4. key record가 남아 있으면 이전 결과를 반환하거나 중복 실행을 억제할 수 있다.
5. key record가 없거나 TTL이 지났으면 같은 문자열이 새 작업으로 처리될 수 있다.

FoundationDB의 `commit_unknown_result`는 이 문제를 데이터베이스 트랜잭션 경계에서 직접 드러낸다. Stripe의 key·parameter 규칙과 HTTP의 멱등성 정의는 API가 이 불확실성을 논리 결과의 재사용으로 다루는 방법을 보여준다. 어느 자료도 모든 외부 부작용에 대한 전역 exactly-once를 약속하지 않는다.

## 안전한 주장으로 좁히기

다음 표현은 범위가 너무 넓다.

> 모든 재시도는 정확히 한 번 실행된다.

대신 다음과 같이 써야 한다.

> 정의된 namespace에서 보존 기간 안에 같은 key와 동등한 매개변수를 가진 재시도는 하나의 저장된 논리 효과로 수렴한다. 데이터베이스 밖의 부작용은 별도의 멱등성·outbox·보상 계약이 필요하다.

이 문장은 검증 가능한 필드를 남긴다. key scope, parameter comparison, retention, in-progress behavior, result replay, downstream propagation, external side-effect boundary를 각각 테스트할 수 있다.

## 운영 선택

멱등성은 재시도 정책과 분리되지 않는다. 재시도 횟수·backoff·jitter·budget를 제한하지 않으면 동일 논리 작업의 중복 억제와 별개로 시스템 부하가 증폭된다. 반대로 모든 재시도를 막으면 일시적 네트워크 실패가 사용자 작업 누락으로 바뀔 수 있다.

따라서 API 설계 문서에는 성공·실패·미확정의 세 결과를 구분하고, 각 결과에서 클라이언트가 어느 key로 어떤 기간 동안 어떤 동작을 반복할 수 있는지 기록해야 한다.
