## 문제 제기

로컬 프로시저 호출과 파일 인터페이스는 강력한 추상화다. 호출자는 인수를 전달하고 결과를 받고, 파일 사용자는 이름으로 데이터를 읽고 쓴다. 같은 프로세스나 한 운영체제 안에서는 실행 위치·실패 관찰·저장 상태의 경계가 비교적 가깝기 때문에 이 추상화가 많은 세부사항을 숨길 수 있다.

그러나 호출과 파일이 네트워크를 넘어 다른 컴퓨터·복제본·데이터센터에 걸치면, 문법은 남아도 전제는 바뀐다. [[Time, Clocks, and the Ordering of Events in a Distributed System]]이 보여 준 단일하지 않은 사건 순서, [[Implementing Remote Procedure Calls]]가 드러낸 응답 부재와 중복 호출, [[The Google File System]]과 [[Dynamo - Amazon's Highly Available Key-value Store]]가 전제로 삼은 구성 요소 실패·복제·버전은 같은 변화를 다른 층에서 보여 준다.

핵심 질문은 “원격 호출은 로컬 호출보다 느리다”가 아니다. 호출·파일·응답이라는 같은 단어가 어떤 결과 계약을 가리키는지 다시 정해야 한다는 것이다.

## 1. 호출 문법은 실행 결과를 보장하지 않는다

RPC는 호출자 스텁, 서버 스텁, 바인딩, 메시지 교환을 통해 원격 연산을 프로시저 호출 형태로 만든다. 이 덕분에 API는 단순해지지만, 호출자는 여전히 원격 주소 공간·서버 큐·네트워크·서버 재시작을 지나 결과를 기다린다.

가장 중요한 차이는 시간 초과의 의미다. 호출자가 응답을 받지 못했다는 관찰은 다음 상태를 구별하지 못한다.

| 호출자가 본 결과 | 원격에서 가능한 상태 | 바로 재시도할 때의 위험 |
|---|---|---|
| 시간 초과 | 요청이 전송되지 않았거나 서버에 도달하지 않음 | 실제로는 문제 없을 수 있지만 추가 부하는 생긴다 |
| 시간 초과 | 서버가 작업 전에 실패하거나 장기간 지연됨 | 재시도와 원래 요청이 경합하거나 순서가 바뀔 수 있다 |
| 시간 초과 | 서버가 작업을 완료했지만 응답이 유실됨 | 같은 상태 변경·결제·메시지가 중복될 수 있다 |
| 오류 응답 | 서버가 요청을 거절했거나 일부 단계만 처리함 | 보상·상태 조회·재처리의 경계를 정해야 한다 |

따라서 “at-most-once”, “exactly-once” 같은 호출 라벨만으로 안전성을 끝낼 수 없다. 어떤 외부 부작용을 하나의 작업으로 볼지, 요청 식별자를 얼마나 보존할지, 중복 제거가 서버 재시작 뒤에도 유지되는지, 취소가 이미 실행된 작업에 어떤 의미를 갖는지 정해야 한다.

## 2. 파일 이름은 하나의 저장 상태를 뜻하지 않는다

[[파일 시스템]]의 파일 이름과 읽기·쓰기 인터페이스는 한 운영체제 안의 장치·디렉터리·권한을 감춘다. [[분산 파일 시스템]]에서는 같은 인터페이스 뒤에 메타데이터 서비스, 청크·블록 서버, 복제본, 캐시, 임대·쓰기 순서, 복구 작업이 더해진다.

GFS는 이 차이를 명확히 보여 준다. 클라이언트는 마스터에서 메타데이터를 얻고 데이터는 청크 서버와 직접 주고받는다. 높은 총 처리량과 장애 허용은 특정 파일 크기·접근 패턴·복제 규칙·실패 처리에 맞춘 결과이며, 어떤 파일 호출에도 즉시 단일하고 영구적인 상태가 보인다는 일반 명제가 아니다.

Dynamo는 키-값 저장에서 같은 문제를 다른 방식으로 드러낸다. 높은 가용성을 위한 복제·버전·정족수형 통신은 동시 갱신의 충돌을 응용 보조 병합으로 남길 수 있다. 따라서 “쓰기 성공”은 적어도 다음 층 중 어디까지를 뜻하는지 밝혀야 한다.

| 층 | 확인된 사실 | 아직 확인되지 않은 것 |
|---|---|---|
| 전송 | 요청이 어떤 서버나 경로에 도달함 | 응용 상태가 유효하게 바뀌었는지 |
| 처리 | 서버가 연산을 실행함 | 다른 복제본과 어떤 순서·버전 관계인지 |
| 내구성 | 선택한 저장·복제 조건이 충족됨 | 모든 관련 작업이 같은 상태를 관찰하는지 |
| 의미 | 응용의 중복·충돌·검증 규칙을 통과함 | 사용자 목적 전체가 완료됐는지 |

## 3. 단일한 시간 대신 순서 계약을 고른다

로컬 실행에서는 프로그램 순서가 많은 경우 충분한 설명이 된다. 분산 환경에서는 [[Time, Clocks, and the Ordering of Events in a Distributed System]]의 happened-before 관계처럼 인과적으로 연결된 사건과 서로 독립적인 사건을 구분해야 한다. 논리 시계로 인과 관계와 모순되지 않는 전체 순서를 만들 수 있지만, 그 순서만으로 실제 시간, 복제 내구성, 응용의 충돌 해결이 결정되지는 않는다.

이 차이는 분산 상태를 설계할 때 세 질문을 분리하게 한다.

| 질문 | 직접 정할 계약 | 대표 수단 |
|---|---|---|
| 어떤 갱신이 원인상 먼저인가 | 인과 관계·메시지 순서 | 논리 시계·요청 식별자 |
| 같은 상태 변경을 누가 어떤 순서로 확정하는가 | 복제·직렬화·정족수 규칙 | [[복제 로그와 합의]], 트랜잭션 |
| 충돌하거나 불확실한 결과를 사용자에게 어떻게 보일 것인가 | 버전·병합·재시도·보상 규칙 | 버전 벡터, 멱등 연산, 응용 검증 |

순서화는 필요할 수 있지만 비용이 없는 배경 기능은 아니다. 리더·정족수·메타데이터·네트워크 경로·재시도는 지연과 자원 비용을 만들고, 어떤 계약을 택했는지에 따라 사용자가 관찰하는 결과도 달라진다.

## 4. 최종 성공은 종단에서 다시 확인한다

[[End-to-End Arguments in System Design]]의 기준으로 보면, 패킷 전달 확인·RPC 응답·청크 서버 수신·복제 확인은 모두 유용한 중간 사실이지만 응용의 최종 성공과 동의어는 아니다. 하위 계층이 실패 빈도와 지연을 낮출 수는 있어도, 응용이 원하는 파일 무결성, 주문 한 번 반영, 작업 결과의 유효성, 여러 상태 변경의 함께 완료를 완결하지는 못한다.

이 원칙은 모든 신뢰성 기능을 응용 코드에 다시 쓰라는 요구가 아니다. 오히려 각 계층의 약속을 정확히 이름 붙이게 한다. 통신 계층은 어떤 전달·순서·재전송을 보장하는가, 저장 계층은 어느 복제·내구성 조건에서 완료를 알리는가, 응용 계층은 어떤 검증·병합·감사·보상을 통해 사용자 결과를 확정하는가를 분리한다.

원격 인터페이스의 좋은 결과 계약은 다음 한 문장으로 시험할 수 있다.

> 같은 요청 식별자와 실패 주입 조건에서, 성공·시간 초과·재시도·복구 뒤 어떤 상태가 어느 복제본에 남고, 사용자는 어떤 결과를 언제 유효하다고 볼 수 있는가?

## 5. 성능은 결과 계약과 함께 측정한다

원격 상태의 성능을 호출당 평균 지연 하나로 비교하면 중요한 비용을 놓친다. 적어도 호출 시작, 서버 수신, 상태 변경 확정, 선택한 내구성 조건 충족, 복제본 가시화, 종단 검증의 시점을 구분해야 한다. 각 시점은 다르게 측정될 수 있고, 제품 계약은 그중 어느 시점을 성공으로 세는지 정해야 한다.

측정 문장에는 작업 종류와 키 분포, 읽기·쓰기 비율, 데이터 크기, 동시성, 복제 수준, 네트워크·서버 실패 주입, 재시도·중복 제거 정책, 일관성·내구성 조건, 평균과 백분위 지연, 충돌·오래된 읽기·시간 초과를 함께 기록한다. 그래야 낮은 지연 수치가 약한 성공 의미나 숨겨진 복구 작업을 가리는 일을 줄일 수 있다.

## 결론

로컬 호출과 파일이 원격 상태가 될 때 잃는 것은 API 자체가 아니라, API 뒤에 암묵적으로 있던 단일 실행 순서·즉시 관찰 가능한 실패·하나의 저장 상태라는 가정이다. 그 빈자리는 인과 순서, 복제·버전, 재시도·중복, 부분 실패, 종단 검증, 복구의 계약으로 채워야 한다.

따라서 분산 시스템의 단순함은 로컬처럼 보이는 API에서 나오지 않는다. 그 API가 숨기는 비용과 실패를 어디까지 드러내고, 누가 어떤 결과를 확인하며, 불확실한 요청을 어떻게 회복하는지 명확히 한 계약에서 나온다.
